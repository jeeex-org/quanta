# Quanta Resilient Skills Design

Learned from Anthropic Cybersecurity Skills (`anthropic-cybersecurity-skills/` cloned in `temp/`) — 818 skills, 34 domains, agentskills.io standard, flat `skills/<name>/` layout (`SKILL.md` + `references/` + `scripts/` + `assets/`). Quanta's version must not become stale the way static SKILL.md files do.

---

## Lessons from Anthropic's design

From `SCOPE.md`: a skill is one named procedure, atomic, executable, distinct, description-routed. From `AGENTS.md`: only `name` + `description` load at discovery (~30 tokens); full body loads only when matched (~500–2000 tokens). Flat namespace — no nesting by domain; `subdomain` frontmatter holds category. From `README.md`: 6 framework mappings (MITRE ATT&CK v19.1, NIST CSF 2.0, MITRE ATLAS, MITRE D3FEND, MITRE AI RMF, MITRE F3 v1.1) — 805/817 mapped to ATT&CK.

From `README.md` and `docs/mitre-f3-mapping.md`: skills carry `mitre_attack`, `atlas_techniques`, `d3fend_techniques`, `nist_ai_rmf`, `nist_csf` frontmatter blocks. Each framework reference lives in `references/standards.md`, verified against official STIX bundles. This is the structure Quanta should adopt — but with resilience, not static duplication.

## Quanta's resilience architecture (not copied from Anthropic)

Anthropic's skills become stale because they are **documents** — Markdown + YAML written once. Quanta's skills must be **derived artifacts** — regenerated from source + roadmap + compiler state.

| Anthropic weakness | Quanta resilience mechanism | Source reference |
|---|---|---|
| Static `SKILL.md` (manual edit) | Skill generated by Phase 2 code synthesizer from `docs/roadmap/domains/*.md` spec + `lib/std/` source | `SELF_IMPROVEMENT.md` Phase 2 |
| `subdomain` field manually maintained | Subdomain derived from domain file path (`programming_language.md` → `subdomain=programming-language`) | `docs/roadmap/domains/` structure |
| Framework mappings hard-coded (`mitre_attack` list) | Framework mappings computed at build time from source: scan `docs/` for framework references (`ATTACK`, `CSF`, `ATLAS`, `D3FEND`, `AI RMF`, `F3`) against current framework versions | `docs/roadmap/quanta.md` framework table |
| `version: "1.2"` in SKILL.md (manual) | Skill version = `VERSION` (e.g., 0.0.166) — single pointer, not per-file | `VERSION` file |
| `references/standards.md` static reference | Reference file regenerated from compiler source (`compiler/0.0.166/src/`) + stdlib (`lib/std/`) by Quanta emitter (`Quanta emitter` prerequisite at 0.0.169) | `SELF_IMPROVEMENT.md` prerequisites |
| `scripts/agent.py` static helper | Script synthesized by test generator (`std/testing`) from `EXPECTED_STDLIB.tsv` gate results — executable only if it passes gate | `SAFETY_MANUAL.md` gate description |
| `assets/template.md` static checklist | Template regenerated from domain spec (`docs/roadmap/domains/*.md`) — changes automatically when roadmap updates | `docs/roadmap/quanta.md` |
| Flat `skills/` directory (no nesting) | Quanta keeps flat `skills/` directory (same convention) but names skills by `DOMAIN.FEATURE` (e.g., `MATH_0.0.001`) per user's code format directive, with domain mapping in `subdomain` field | User memory directive: `DOMAIN.MAJOR.MINOR-ITEM` |

## Skill lifecycle (resilience loop, pure Quanta — no Python)

```
Roadmap domain file (docs/roadmap/domains/*.md) → spec
Compiler source (compiler/0.0.166/src/) + stdlib (lib/std/) → implementation proof
Gap detector (SI Phase 1, pure Quanta, no Python bootstrap) → detects 🔲 planned vs ✅ done
Spec-to-IR mapper (SI Phase 2 prerequisite, `std/ir`) → generates Quanta IR for missing modules
Pattern library (`std/patterns`) + code synthesizer → produces Quanta source (.quanta file)
Quanta emitter (`compiler` + `std/ast` + `std/print`) → writes skills/<DOMAIN.FEATURE>/SKILL.md + scripts/
Test generator (`std/testing` + test/) → writes EXPECTED_STDLIB.tsv row + verification test
Merge automation (`std/git` + `std/ci`) → commits, bumps VERSION, marks domain ✅
Self-hosting fixpoint: qc (current) compiles generated skill → binary runs → result verified
```

If any framework version updates (e.g., MITRE ATT&CK v19.2), the loop regenerates affected skills automatically — no manual edit of SKILL.md frontmatter. The framework mapping is a derived property, not a maintained list.

## Structure for Quanta skills

Adopt Anthropic's flat directory convention (proven scalable to 818 skills) but with Quanta naming:

```
skills/MATH_0.0.001-vector_spaces/
├── SKILL.md                 # Generated from domain spec + compiler source
│                             # YAML frontmatter: name, domain=MATH, subdomain=algebra,
│                             # tags=[vector-spaces, linear-algebra],
│                             # framework mappings (derived at build time)
├── references/
│   ├── standards.md          # Generated: framework references from current versions
│   └── source_ref.md         # Generated: points to compiler/${VERSION}/src/ lines + lib/std/
├── scripts/
│   └── verify.quanta         # Generated: executable test script (not .py — pure Quanta)
│                             # Runs against EXPECTED_STDLIB.tsv row
└── assets/
    └── template.md           # Generated: checklist/template from domain spec
```

No `LICENSE` per skill (Quanta uses project-level Apache-2.0 per `VERSION` pointer). No `assets/template.md` unless the domain spec defines one. The flat namespace is critical — Anthropic's `skills/` directory has 818 entries without nesting; Quanta's 97 domain files must also stay flat.

## Resilience rules (from Anthropic + Quanta sources combined)

1. **No static skill files in source control** — `skills/` directory contents are build artifacts (like `compiler/0.0.166/bin/x86/qc` binary), not source. Source is `docs/roadmap/domains/*.md` + `compiler/` + `lib/std/`. Skills regenerate at build.

2. **Skill is executable proof, not documentation** — `SKILL.md` describes what the compiler/stdlib does (like Anthropic's procedure), but the verification is the binary output from `qc`. If the compiler changes, the skill description updates automatically from the new source.

3. **Framework mappings derived, not authored** — scan framework STIX bundles at build time (same mechanism Anthropic uses with `mitreattack-python`), not maintained by hand. The mapping lives in the build, not in `.md`.

4. **Version pointer single** — `VERSION` points to latest stable. All skills reference it (`VERSION` in SKILL.md frontmatter). When `VERSION` bumps, every skill is stale by design until rebuilt — visible failure, not hidden decay.

5. **Gap detection automatic** — `SELF_IMPROVEMENT.md` Phase 1 (pure Quanta, no Python) reads domain files. If a 🔲 planned module has no corresponding `skills/DOMAIN.FEATURE/` directory, it's an open gap — same visibility as Anthropic's `ATTACK_COVERAGE.md` table but automatic.

6. **Pure Quanta, no Python bootstrap** — Anthropic uses `python tools/validate-skill.py`. Quanta's equivalent (`test_suites/scripts/fuzz_differential.sh` + `EXPECTED_STDLIB.tsv`) runs as a Quanta binary. The `python` dependency is removed — matching user's directive: "SI must be pure Quanta, no Python".

## What Quanta does NOT adopt from Anthropic

- Anthropic's `skills/` flat directory holds 818 manual files. Quanta's `skills/` holds 0 source files — all generated. The domain coverage (34 cybersecurity domains in Anthropic vs 97 in Quanta) is wider in Quanta but all planned (🔲), not executed.
- Anthropic has executable scripts (`scripts/agent.py`, `scripts/process.py`). Quanta's equivalents are Quanta source files (`.quanta`) compiled by `qc` — no `.py` dependency.
- Anthropic's framework mappings reference MITRE v19.1 specifically. Quanta's framework mappings are build-time derived (scan framework STIX bundles against source) — version-agnostic by design.
- Anthropic's skills reference real practitioner workflows (Volatility3, Sigma rules, BloodHound). Quanta's skills reference compiler/stdlib capabilities (`fconst`, `kv_cache_store`, `NF4_dequant`) — the brain substrate, not the practitioner procedure. Once `ai_llm` core lands (0.163–0.172), Quanta skills can encode practitioner-level procedures; today they encode compiler-level capabilities.
